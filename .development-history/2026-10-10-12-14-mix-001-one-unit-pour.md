# MIX-001 one-unit pour input

## Task summary
Make one pour input transfer exactly one material unit, and prepare the MIX-001 work for review.

## Relevant previous context
- MIX-001 (#17) uses the isolated `Dev_DePo4l_MIXER` scene and the prototype recipe of one cement plus one sand, yielding two concrete units.
- Earlier reports document the mixer state machine, staged buckets, player input activation, status feedback, and automatic mixing after a complete recipe arrives.
- The previous input path treated a held pour action as a continuous request, which could transfer multiple units from one press.

## Changes made
- Added a one-unit transfer request to `BucketPourAction`, while keeping its existing continuous `RequestPour` behavior for other callers.
- Changed `BucketPourInput` to react to the input press edge and make one single-unit request.
- Updated Play Mode coverage to assert one unit per request and preserve the unit already transferred when the bucket is dropped.

## Files affected
- `Assets/Game/Scripts/Material/BucketPourAction.cs`
- `Assets/Game/Scripts/Material/BucketPourInput.cs`
- `Assets/Game/Tests/Material/BucketPourPlayModeTests.cs`
- This report.

## Technical decisions
- A press transfers one unit immediately; holding the key does not start the continuous transfer path.
- Existing callers of `BucketPourAction.RequestPour` keep continuous behavior, limiting the behavior change to the player input facade.
- No package, serialized asset, or networking code was added for this change.

## Verification performed
- Unity Editor 6000.3.25f1 recompiled successfully; `compilationFailed` was false and the Console had zero errors and warnings at the final check.
- Play Mode test `PourInputRequiresCarriedBucketAndStopsWhenReleased` passed 1/1.
- Play Mode test `DroppingHeldBucketAfterOneShotPourKeepsOnlyTheUnitAlreadyTransferred` passed 1/1.
- In `Dev_DePo4l_MIXER` Play Mode, a runtime grab followed by one `BucketPourInput.RequestPour` call changed the sand bucket from five units to four and the mixer from zero to one.
- The Game View showed the mixer status panel in the isolated scene. The scene was returned to Edit Mode with its saved test materials intact.
- Keyboard events injected through the CLI did not reliably reach the per-frame input handler, so the runtime scene check called the same input facade method directly.

## Final result
The single-unit path and its drop behavior pass their focused Play Mode tests. The runtime scene check also confirmed one request moves one sand unit into the mixer.

## Known limitations
- A human keyboard-and-mouse playtest of aiming, grabbing, and pressing `R` remains unverified; the CLI key simulator did not provide a reliable frame-timed input event.
- Mixer feedback and recipe completion were verified in earlier MIX-001 reports through the runtime container API, not a physical keyboard session.

## Unresolved issues or follow-up work
- Have a reviewer try the full grab-and-pour flow in Unity and check the gameplay feel before merge.
- Existing unrelated local edits to the scaffold scene and `ProjectSettings/` were left unstaged and are not part of this report's change.
